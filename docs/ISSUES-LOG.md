## ISS-001: סוג ערך שגוי ב-aggregateRating (Schema.org)

| שדה | פרטים |
|-----|-------|
| **תאריך גילוי** | 2026-02-19 (Google Search Console) |
| **תאריך תיקון** | 2026-02-22 |
| **חומרה** | קריטית |
| **קטגוריה** | SEO / נתונים מובנים |
| **קבצים מושפעים** | `index.html` |
| **commit שיצר את הבעיה** | `ef10a36` (2026-02-16) |
| **commit שתיקן** | `a86bee0` (2026-02-22) |

### תיאור הבעיה
ערכי `aggregateRating` ב-JSON-LD הוגדרו כמחרוזות (string) במקום מספרים (number):
```json
// שגוי:
"ratingValue": "5",
"bestRating": "5",
"ratingCount": "6",
"reviewCount": "6"
```

### סיבת שורש
טעות בכתיבת JSON-LD - הוספת מרכאות סביב ערכים מספריים. ב-JSON יש הבדל בין `"5"` (string) ל-`5` (number). Google Schema Validator דורש Number עבור שדות מספריים.

### פתרון
הסרת המרכאות מהערכים המספריים:
```json
// תקין:
"ratingValue": 5,
"bestRating": 5,
"ratingCount": 6,
"reviewCount": 6
```

### מניעה לעתיד
- **כלל**: ערכים מספריים ב-JSON-LD (rating, count, price) חייבים להיות ללא מרכאות
- **בדיקה**: לפני push של שינויי Schema.org - להריץ בדיקה ב-[Rich Results Test](https://search.google.com/test/rich-results)
- **תבנית**: להשתמש בתבנית הנכונה מ-schema.org/AggregateRating

## ISS-006 — רגרסיית CLS מ-critical-CSS (07/06/2026)

### תיאור
שינוי "critical-CSS" (הטמעת CSS קריטי inline + טעינת ה-stylesheet אסינכרונית) שיפר LCP, אבל גרם ל-CLS לקפוץ מ-0.006 ל-~1.0 (קפיצות עיצוב חמורות) ו-Performance צנח 90→60. נתפס רק בדוח השבועי, ימים אחרי הדחיפה.

### סיבת שורש
השינוי נבדק לפני המיזוג על LCP/FCP/TBT בלבד — **CLS לא נבדק**. ה-swap האסינכרוני של ה-stylesheet הזיז את הפריסה כשה-CSS המלא נטען.

### פתרון
ביטול ה-critical-CSS (commit `756d3a2`) — חזרה ל-CSS חוסם רגיל. CLS חזר ל-0.013, Performance ל-95.

### מניעה לעתיד
- `check-site.mjs` (בדיקה יומית) בודק עכשיו **גם CLS** — median של 3 דגימות, מתריע אם CLS>0.25. רגרסיה כזו תיתפס תוך 24 שעות אוטומטית.
- **כלל**: כל שינוי ביצועים נמדד על **כל** ה-Core Web Vitals (LCP + CLS + TBT), לא רק על המדד שמנסים לשפר.

## ISS-007 — המחשבון לא היה בדפים שמביאים את התנועה (13/07/2026)

### תיאור
מחשבון מחיר בור החלחול נבנה (05/07) ונפרס בדף השירות `drainage-pits` בלבד. דוח Search Console של יוני חשף ש-**76% מהקליקים (72 מתוך 95) מגיעים מ-3 מאמרי מחיר בבלוג** — ו-`drainage-pits-pricing` לבדו מביא 30 קליקים, מדורג על "קידוח בור חלחול מחיר". כלומר: המבקרים הכי חמים באתר — אלה שחיפשו בגוגל בדיוק את השאלה שהמחשבון עונה עליה — מעולם לא ראו אותו.

### סיבת שורש
המחשבון שובץ לפי **מבנה האתר** (דף השירות הוא ה"בית" הטבעי של הנושא) ולא לפי **נתוני התנועה בפועל**. אף אחד לא הצליב את מיקום הפיצ'ר עם הדוח של Search Console. הבלוג נתפס כתוכן SEO משני, בעוד שבפועל הוא שער הכניסה הראשי.

### פתרון (commit `0b9b340`)
- `blog/drainage-pits-pricing` — המחשבון **מוטמע** מיד אחרי טבלת המחירים, במקום CTA גנרי של "צרו קשר". זה הרגע שבו הקורא סיים לקרוא מחירים כלליים ושואל "כמה זה יעלה **לי**".
- `blog/drainage-pits-guide` — קישור בולט מסעיף העלויות (מזין גם קישורים פנימיים לעמוד העצמאי כדי שידורג).
- **הגנת פופאפ:** שני הפופאפים (טיימר 45ש', גלילת 40%) היו נוחתים בדיוק על המחשבון — 40% גלילה זה בדיוק המיקום שלו עכשיו. פופאפ שמבקש טלפון ומסתיר את האומדן מתחרה בעצמו. המחשבון שולח `pcEngaged` ב-postMessage בלחיצה הראשונה; הפופאפים נדחים כל עוד הוא על המסך, ומושתקים לגמרי ברגע שהמבקר התחיל לחשב.

### מניעה לעתיד
- **לפני שמחליטים איפה לשבץ פיצ'ר שמייצר לידים — לפתוח את דוח Search Console ולשבץ אותו בדפים שמביאים את הקליקים, לא רק בדף ה"נכון" לפי מבנה האתר.**
- כל פופאפ/אוברליי חדש חייב להיבדק מול הרכיבים האינטראקטיביים בעמוד. שתי מלכודות לידים שנפתחות באותו רגע = אפס לידים.
- אומת בדפדפן אמיתי על פרוד: האומדן מוצג (₪7,000–12,000), אין פופאפ מעל המחשבון, והפופאפ עדיין קופץ כרגיל בדפים בלי מחשבון.
