## ISS-011: רשימות `.service-features` נשברו ב-RTL (רווח ענק אחרי התווית המודגשת)

| שדה | פרטים |
|-----|-------|
| **תאריך גילוי** | 2026-07-17 (אליאב, צילום מסך של דף `drainage-pit-home`) |
| **תאריך תיקון** | 2026-07-17 |
| **חומרה** | בינונית (ויזואלי, פוגע באמינות) |
| **קטגוריה** | UI / RTL / CSS |
| **קבצים מושפעים** | `css/style.css` (`.service-features li`), כל דפי השירות |
| **commit שתיקן** | ראה למטה |

### תיאור הבעיה
בפריט `<li><svg>…</svg><strong>תווית</strong> — טקסט</li>`, ה-`li` הוגדר `display:flex; gap:12px`. ב-flex, ה-`<strong>` והטקסט שאחריו הם **שני פריטי-flex נפרדים** (הטקסט הופך ל-anonymous flex item). כשהתווית ארוכה, הטקסט "נזרק" לשורה נפרדת ונוצר **רווח לבן ענק** אחרי התווית המודגשת. הופיע חזק ב-RTL עם תוויות ארוכות.

### סיבת שורש
`display:flex` על ה-`li` אינו מתאים לתוכן inline מעורב (אלמנט מודגש + טקסט חופשי). flex מפצל כל רצף לפריט נפרד. הבאג היה **סמוי בכל דפי השירות** — התגלה רק כשהתוכן היה ארוך מספיק כדי לגלוש.

⚠️ **לקח ספציפיות (חשוב!):** בניסיון הראשון תיקנתי את `.service-features li` — אבל הרשימות יושבות בתוך `.service-detail-card`, ויש כלל **ספציפי יותר** `.service-detail-card ul li{display:flex}` (0,1,2 מול 0,1,1) שדרס אותו. התיקון "עבד" רק על רשימה שהיתה עטופה ב-`<span>` (שם flex לא מזיק כי הכל פריט אחד), ולכן חשבתי שהוא תקין — עד שהמשתמש הצביע על רשימה לא-עטופה. **מוסר: כשתיקון CSS "לא נתפס", לחפש סלקטור ספציפי יותר עם `getComputedStyle` + לאמת ויזואלית את *כל* המופעים, לא רק אחד.**

### הפתרון
שינוי הכלל הנכון `.service-detail-card ul li` (וגם `.service-features li`) מ-`display:flex` ל-`display:block` עם אייקון ב-`position:absolute; inset-inline-start:0; top:13px` ו-`padding-inline-start:32px`. כך הטקסט זורם כתוכן inline רגיל **ללא תלות באורך או בעטיפת span**. מתקן את **כל** דפי השירות. אומת ויזואלית: dph (רשימה ממוספרת) + drainage-pits (ללא רגרסיה), מובייל 390.

### 🛡️ מניעה (GUARD)
1. **לעולם לא `display:flex` על אלמנט שמכיל אלמנט-inline + טקסט-אח** (strong/a/b ואז טקסט). להשתמש ב-block+absolute-icon או לעטוף הכל ב-`<span>` יחיד.
2. **חובה אימות ויזואלי (screenshot דסקטופ+מובייל) לכל דף/רכיב חדש לפני "מוכן"** — הבאג הזה נוצר כי דילגתי על הצילום. זה מעוגן ב-[[eliavafar_site_health_protocol]] ובפרוטוקול העבודה.
3. תבנית `<strong>תווית</strong> — טקסט` בתוך flex = דגל אדום. לחפש `grep "display: flex" ליד רשימות תוכן.

## ISS-001: סוג ערך שגוי ב-aggregateRating (Schema.org)

| שדה | פרטים |
|-----|-------|
| **תאריך גילוי** | 2026-02-19 (Google Search Console) |
| **תאריך תיקון** | 2026-02-22 |
| **חומרה** | קריטית |
| **קטגוריה** | SEO / נתונים מובנים |
| **קבצים מושפעים** | `index.html` |
| **commit שיצר את הבעיה** | `ef10a36` (2026-02-16) |
| **commit שתיקן** | `a86bee0` (2026-02-22) |

### תיאור הבעיה
ערכי `aggregateRating` ב-JSON-LD הוגדרו כמחרוזות (string) במקום מספרים (number):
```json
// שגוי:
"ratingValue": "5",
"bestRating": "5",
"ratingCount": "6",
"reviewCount": "6"
```

### סיבת שורש
טעות בכתיבת JSON-LD - הוספת מרכאות סביב ערכים מספריים. ב-JSON יש הבדל בין `"5"` (string) ל-`5` (number). Google Schema Validator דורש Number עבור שדות מספריים.

### פתרון
הסרת המרכאות מהערכים המספריים:
```json
// תקין:
"ratingValue": 5,
"bestRating": 5,
"ratingCount": 6,
"reviewCount": 6
```

### מניעה לעתיד
- **כלל**: ערכים מספריים ב-JSON-LD (rating, count, price) חייבים להיות ללא מרכאות
- **בדיקה**: לפני push של שינויי Schema.org - להריץ בדיקה ב-[Rich Results Test](https://search.google.com/test/rich-results)
- **תבנית**: להשתמש בתבנית הנכונה מ-schema.org/AggregateRating

## ISS-007 — המחשבון לא היה בדפים שמביאים את התנועה (13/07/2026)

### תיאור

### פתרון (commit `0b9b340`)

### מניעה לעתיד
- **לפני שמחליטים איפה לשבץ פיצ'ר שמייצר לידים — לפתוח את דוח Search Console ולשבץ אותו בדפים שמביאים את הקליקים, לא רק בדף ה"נכון" לפי מבנה האתר.**

## ISS-008 — ביקורת מקיפה: אבטחה, ביצועים, SEO (13/07/2026)

### תיאור
סריקה כללית של האתר בארבעה צירים. אותרו 3 פערי אבטחה אמיתיים, 4 חסמי ביצועים, ותקלה שקטה שבה לידים לא נכנסו לרשימת התפוצה.

### ממצאי אבטחה + פתרון (commit `1b30bd7`)
1. **אין הגבלת קצב על ה-endpoints הציבוריים.** אומת חי: 5 בקשות POST רצופות ל-`/api/notify-lead` — כולן 200, אפס חסימה. כל בקשה שולחת מייל אמיתי דרך Brevo ⇒ ה-endpoint היה **דיוור חינם** לתוקף: אפשר לשרוף את מכסת Brevo ולהטביע לידים אמיתיים בזבל. נוסף `lib/rate-limit.js` — 5 בקשות/10 דק' לכל כתובת IP + תקרת 40 למופע, לפני כל קריאה ל-Brevo. אומת בפרוד: בקשה 6 → 429.
2. **הזרקת קוד למייל ההתראה שלנו עצמנו.** `phone` נוקה מרווחים/מקפים אך **לא** נמלט, והושתל ישירות לתוך `href="..."`. טלפון מעוצב יכול היה לסגור את התכונה ולהזריק event handler למייל שנשלח לבעלים. תוקן בשורש: מספר טלפון = ספרות, אז מסננים הכל חוץ מספרות לפני שהוא מגיע ל-href.
3. **שגיאות upstream מילוליות.** שני ה-endpoints החזירו את הודעת השגיאה הגולמית של Brevo ללקוח (יכולה לחשוף מצב מפתח/מכסה). עכשיו נרשם בצד שרת, 502 גנרי ללקוח.
4. postMessage ללא בדיקת origin — נוספה בדיקה. לא היה נצול בפועל (X-Frame-Options חוסם מסגור חוצה-מקור, וכל 78 הקישורים עם `target=_blank` נושאים `rel=noopener`), אבל מאזין לא אמור לתת אמון במקור לא-מאומת.

### 🔴 תקלה שקטה — לידים לא נכנסו לרשימת התפוצה (אותרה תוך כדי)
`api/subscribe.js` שלח ל-Brevo בקשה **בלי שום מזהה** כשלא היה אימייל — רק `attributes.PHONE`. Brevo דורש `email` או `ext_id`. מאחר שהאימייל הפך ללא-חובה בטופס (שינוי CRO מיוני), **רוב הלידים מגיעים עם טלפון בלבד ⇒ אף אחד מהם לא נוסף לרשימת אנשי הקשר.** הליד עצמו כן הגיע לבעלים (נתיב נפרד, `notify-lead`) אז לא אבדו פניות — אבל רשימת התפוצה לא נבנתה חודשים. תוקן: `ext_id` = הטלפון בפורמט בינלאומי + attribute `SMS`. אומת בפרוד: טלפון-בלבד מחזיר עכשיו 200 (קודם נכשל).

### תוספת ל-ISS-008 — הגנת ספאם: מה באמת נחוץ (13/07, אחרי התייעצות)

5. **תקרת נזק טבעית:** התוכנית החינמית של Brevo חוסמת ב-300 מיילים ליום. גם הצפה מוצלחת מוגבלת לזה.

## ISS-024 — 4 רגרסיות מ-PR #42: FAQ לא מלא רוחב, רשת שירותים שבורה, checkmark מכסה מספרים, ולידציה חסרה (06/09/2026)

### תיאור הבעיות

#### בעיה 1: שאלות FAQ לא ממלאות רוחב מלא
כפתורי ה-FAQ (`.faq-question`) הומרו ל-`<button>` עבור נגישות (`aria-expanded`) ב-PR #42, אבל **לא נוסף `width: 100%`**. התוצאה: תיבה קטנה מיושרת לצד (RTL) עם רווח לבן גדול משמאל. הבעיה בכל 28 דפי האתר שמכילים FAQ.

**סיבת שורש:** כאשר `<div>` הופך ל-`<button>`, ברירת המחדל של הדפדפן היא `width: auto` ולא stretch מלא. ה-CSS לא התעדכן להתאים להמרה.

**תיקון:** נוסף ל-`.faq-question` ב-`css/style.css`:
- `width: 100%` — מילוי רוחב מלא
- `border: none` — הסרת הגבול הדפולטיבי של button
- `text-align: inherit` — ירושת כיוון טקסט RTL
- `font-family: inherit` — ירושת משפחת גופן

#### בעיה 2: רשת השירותים בעמוד הבית — כרטיס 4 נראה יתום
בעמוד הבית יש 4 כרטיסי שירות ב-`.service-summary-grid`. ה-grid הוגדר `repeat(auto-fit, minmax(280px, 1fr))` שפיצל ל-3 כרטיסים בשורה ראשונה + 1 כרטיס בשורה שנייה מיושר לצד. נראה לא מושלם ויוצר תחושה של עיצוב שבור.

**סיבת שורש:** `auto-fit` עם `minmax()` לא מבטיח מספר עמודות קבוע. עם 4 כרטיסים, התפלגות 3+1 היא תוצאה מתמטית של הגבולות.

**תיקון:** שינוי ל-`grid-template-columns: repeat(2, 1fr)` — רשת קבועה של 2×2 בדסקטופ. במובייל (`max-width: 768px`) נשאר `1fr` (עמודה אחת).

#### בעיה 3: checkmark במחשבון בור החלחול מכסה את המספרים
ב-`drainage-calculator.html`, כאשר משתמש בוחר אופציה (למשל "12 מ'" או "1 מ'"), ה-checkmark (✓) מופיע ב-`position: absolute` עם `inset-inline-start: 8px` (צד שמאל ב-RTL) ו-`top: 6px`. במיקום זה, הוא **מכסה בדיוק** את הספרות של המספרים.

**סיבת שורש:** המיקום נבחר מבלי לבדוק חפיפה עם התוכן הטקסטואלי באופציות הקטנות (grid של 4).

**תיקון:** שינוי `inset-inline-start` ל-`inset-inline-end` — הצ'קמארק עובר לצד הנגדי (ימין ב-RTL, שמאל ב-LTR) ולא מכסה את הטקסט.

#### בעיה 4: חוסר ולידציה בשדות טלפון ואימייל
כל הטפסים באתר (contact, service pages, popups, calculator) **לא מאמתים קלט** בצד לקוח:
- שדות `type="tel"` מקבלים אותיות עבריות, אנגליות, תווים מיוחדים — כל דבר
- שדות `type="email"` לא מציגים הודעת שגיאה בעברית כשהפורמט לא תקין

**סיבת שורש:** התבססות על HTML5 validation בלבד, ללא JS להוספת `pattern`, `inputmode`, וניקוי קלט בזמן אמת.

**תיקון ב-`js/main.js`:**
```javascript
// טלפון: ספרות, +, רווחים, מקפים בלבד
input.setAttribute('inputmode', 'tel');
input.setAttribute('pattern', '[0-9+\\s\\-]+');
input.addEventListener('input', e => {
  e.target.value = e.target.value.replace(/[^0-9+\s\-]/g, '');
});

// אימייל: הודעה בעברית על שגיאה
input.addEventListener('invalid', e => {
  if (e.target.value !== '') {
    e.target.setCustomValidity('נא להזין כתובת אימייל תקינה (לדוגמה: example@email.com)');
  }
});
```

### מניעה לעתיד
1. **כשהופכים אלמנט ל-`<button>` לצורך נגישות** — תמיד להוסיף CSS reset: `width`, `border`, `background`, `text-align`, `font-family`
2. **Grid עם `auto-fit`** — לבדוק התנהגות עם מספרי פריטים שונים (3, 4, 5...) ולא רק עם המספר הנוכחי
3. **Position absolute על תוכן דינמי** — תמיד לאמת שהוא לא מכסה טקסט בכל הווריאציות (ארוך/קצר, מספרים/מילים)
4. **Validation של טפסים** — לבדוק בפועל בדפדפן שהקלט נחסם, לא רק לראות שה-HTML5 attribute קיים
